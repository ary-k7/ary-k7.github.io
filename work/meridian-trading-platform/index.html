Meridian: an execution platform built to a written specification

A self-hosted platform for running rules-based option strategies, designed around no duplicate orders, crash recovery and broker reconciliation. I did not write a single line of its code; I wrote the spec and tokenmaxxed through Fable and Opus.

The question

I wanted to know whether a rules-based option strategy could be run by a system I specify, with no duplicate orders, recovery after a crash and reconciliation against the broker’s records.

I did not write a single line of code for it. I wrote the specification and tokenmaxxed through Fable and Opus: about 89,000 lines across 832 commits in five days. What this page shows is how I specify and review a system, not how I type.

What I did

I directed the specification, then had it implemented under review gates. The roles are explicit in the project: I am the owner, one AI model acts as architect and reviews each phase, and another implements it.

  • Specification set. A product requirements document, a binding architecture in 22 sections, a database schema, API contracts, a broker-integration spec, a testing strategy, a phased roadmap with architect-reviewed gates, and logs of decisions and deviations.
  • Design rules.
    • Every order state is committed to the database before the network call, so that after a crash the system knows about every order it may have sent.
    • Strategies run as pure reducers, with no wall-clock calls in domain code, so they can be replayed and tested deterministically.
    • Broker-specific code lives only in adapters.
  • Regulation in the design. The 2025 SEBI framework for retail algorithmic trading, static-IP whitelisting and a cap of 10 orders a second are requirements, not afterthoughts.

The performance targets are design targets, not measurements: p99 order latency of 30 ms or less, zero duplicate orders, and recovery within 60 seconds of a crash. I have not yet shown that the system meets them.

What would break this

  • Age. The platform is five days old, and the final gate in its roadmap has not been passed.
  • Authorship. Fable and Opus wrote all of the code. My contribution is the specification, the design decisions and the review, and that is how I describe it.
  • Unmeasured targets. Until latency, duplicate-order and recovery tests are run under load, the targets are intentions.
  • Review depth. Review gates catch what the reviewers look for. Code written at the pace of 832 commits in five days cannot all be read line by line by one person.

What I would do next

Run fault-injection tests for the recovery and no-duplicate guarantees, and publish the measured figures beside the targets.
